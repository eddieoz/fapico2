===== Conclusions (US-1711, recorded 2026-10-15) =====

The page constant chosen for every later story: **page 58 is taken; the custody
ceremony compiles page 59** (rows 0xEC0-0xEBF is page 58's own range; page 59 is
rows 0xEC0-0xEFF, free and unlocked — every row in it read 0x000000 in both
views). No page above 59 is needed: page 59 alone holds 64 rows = 128 bytes.

Measured facts on the pico-fido2-migrated board (BOOTSEL, reads only, no SWD
debugger attached — the AGENTS.md hardware warning is honoured):

1. **Page 58 post-lock demonstrated.** Every row of page 58 (0xE80-0xEBF,
   64 rows) is refused to picotool with "permission failure" in BOTH the raw
   and ECC views. The shipping firmware's ECC path reads 0xE90-0xE9F fine at
   boot — boot.rs's read_otp_key_1 is the in-tree witness. This is exactly
   the post-lock state the custody rows will live in, demonstrated at zero
   risk: locked-to-outsider, readable-to-holder-of-the-software-lock.

2. **The lock row and its value are confirmed, not folklore.** Row 0xFF5
   (picotool names it OTP_DATA_PAGE58_LOCK1) reads 0x3c3c3c —
   LOCK_BL=3, LOCK_NS=3, LOCK_S=0 — matching
   docs/pico-fido2-to-fapico2-migration.md:49 exactly. The C's formula
   `OTP_DATA_PAGE0_LOCK0_ROW + page*2 + 1` lands on 0xFF5 because
   picotool's own field naming shows the lock-row base is **0xF80**
   (PAGE56_LOCK0 sits at 0xFF0 = 0xF80 + 56*2), not 0xFF0/0xFF4 as an
   off-the-name-table reading suggests. An earlier parse in this transcript
   reported the lock rows as 0x000000; that was a `-n` output-format parse
   bug in scripts/otp_probe.py's row_value() — the fields view above is
   authoritative and the parser has been checked against it.

3. **Factory locks, not ours:** PAGE62_LOCK1 (0xFFD) = 0x040404,
   PAGE63_LOCK1 (0xFFF) = 0x141414 — bootrom-critical locks that ship on
   every RP2350. They bound nothing we need: pages 59-61 remain free.

4. **Erased rows read ZERO, not all-ones.** Every candidate row in pages
   59-61 (0xEC0-0xF7F) and the unburned lock rows read 0x000000 in the raw
   view. This matches pico-fido2's `is_empty_buffer` (zero bytes = empty)
   and inverts the assumption US-1710's classifier was written under:
   raw all-ones on this silicon is the **debug-refusal artifact** (the
   probe-rs/OTP_DATA_RAW pathology in AGENTS.md), not the erased mark.
   Consequence, recorded for otp_cus.rs: **Erased = raw view reads
   zero-bytes; an all-ones raw row classifies Faulted/refused, never
   Erased.** US-1712's refill loop keys on this — an erased-class word is
   refillable, a faulted one must abort the ceremony.

5. **The register model reconciles to 64 pages x 64 rows.** embassy-rp's
   declarations (NUM_PAGES=64, NUM_ROWS_PER_PAGE=64) and picotool's row
   naming agree on every row both can read; the 256x16 hypothesis is dead.
   ADR 0004 am2's question is answered: row index = page*64 + row-in-page,
   lock rows at 0xF80 + page*2 (+1 for LOCK1).
